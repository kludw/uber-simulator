# Architecture

What lives where and how it connects. Behavior: [spec.md](spec.md). Why: [ADRs](adr/README.md). Terms: `.claude/skills/domain/SKILL.md`.

Current state: milestones 2 to 16 done. `bun run sim` runs everything in one process over an in-memory bus, or with `--bus nats` each service on its own NATS connection. Each service also runs as its own process over NATS ([0019](adr/0019-single-package-multiple-entrypoints.md), [0028](adr/0028-nats-bus-subjects-and-delivery.md)), all spawned by `bun run dev`. Integration tests check invariants on NATS runs. `bun run ui` serves the browser UI, which subscribes to NATS events over WebSocket. The persister (also spawned by `bun run dev`) stores every event from a JetStream stream into the ClickHouse `events` table; `bun run report` queries it per run. Dispatch matches greedily or in batches, chosen per run (`--matching` / `MATCHING`, [0030](adr/0030-batched-matching.md)); `bun run sim -- --compare` runs both in process on one seed side by side. Rider demand model (uniform or `city` hotspots, [0031](adr/0031-hotspot-demand.md)), demand rate, and fleet size are chosen per run too (`--demand` / `DEMAND`, `--requests-per-minute`, `--drivers-per-shard`), and so are driver shifts (`--shifts` / `SHIFTS`, [0032](adr/0032-driver-shifts.md)) and preferences (`--preferences` / `PREFERENCES`, [0035](adr/0035-driver-preferences.md)). `bun run replay` republishes a stored run on `replay.<runId>.*` and the UI watches it with `?replay=<runId>` ([0034](adr/0034-replay.md)). Local NATS and ClickHouse run via Docker Compose (see Local infra).

| Dispatch brain | `src/dispatch/brain.ts`, `trip.ts` | owns every trip of its region: queue, offers, matching (`matching` start config: greedy default, or batched every `windowTicks`), pickup, completion, cancel. `regions` / `region` start config: the layout and the region it owns (one region by default). | Idle driver index | `src/dispatch/idle-drivers.ts` | dispatch's drivers in its region (`startIdleDrivers(grid, region)`, the whole grid by default) across ticks, updated in place: known cells, kept as x and y numbers (`placeDriver` on going online or moving, `removeDriver` on going offline), busy drivers (`markBusy` only an idle driver, `markFree` only a busy one, else it throws), drivers outside the region dropped (`placeDriver` there drops a driver unless busy, never adds one; a busy one keeps its record until `markFree`, which drops it if still outside; a region's sides on the grid's edges are open, so a cell off the grid stays as with one region), and the idle ones (known, not busy) in a uniform grid (8 × 8 cells per bucket), each bucket entry knowing its slot so leaving is a swap. `nearestIdle(drivers, pickup, excluded)` returns the nearest idle driver not excluded, ties to the lowest ID, exactly what a linear scan returns: searches square rings of buckets until nothing farther out can be as near, or scans linearly below 64 idle drivers; `nearestIdleSkipping(drivers, pickup, skip)` is the same search skipping the drivers a predicate holds for, returning the driver with its cell (batched matching's nearest untouched driver); `idleCount` counts the idle drivers; `idleDriversById` lists them for batched's dense case. A driver cell off the grid (bad input) goes to the nearest edge bucket, distances still from its true cell, so the result stays exact; a pickup off the grid takes the linear scan. | Matching solver | `src/dispatch/matching.ts` | `minCostMatching(rows, columns, { ofRow, ofColumn })`: pure Hungarian solver for the batch assignment, maximum cardinality first, then least total cost; an `Infinity` cost is a pair not allowed; throws on negative / non-integer costs. Asks the caller to fill one row's costs at a time (one column's when rows outnumber columns) and never stores the matrix, so memory is O(rows + columns) ([#213](https://github.com/kludw/uber-simulator/issues/213)). Runs on the rectangular problem (smaller side as rows, transposed if needed, no padding): O(rows² × columns). Used by dispatch in batched mode when more trips are queued than drivers are idle. `minCostMatchingByNearest(trips, nearest, grid)`: same objective for queued trips (pickup, excluded drivers) over idle drivers it never lists: exact shortest augmenting paths with potentials over the drivers some path has reached (touched), plus each visited trip's nearest untouched allowed driver from the `nearest(pickup, skip)` callback (cached per trip until that driver is touched), else any untouched driver at the sentinel cost (trips × (grid width + height − 2) + 1, which assumes every cell is on the grid: an off-grid cell is bad input, and with one a batch may get fewer pairs than the dense solver's); a trip found to have no allowed untouched driver isn't queried again in the batch; needs at least as many idle drivers as trips, else throws. Doesn't import the index. Used by dispatch in batched mode otherwise | [0030](adr/0030-batched-matching.md), [0033](adr/0033-scale-fixes.md), [0051](adr/0051-search-untouched-drivers-in-batched-matching.md) |

## Data flow

```
bun run sim -> main.ts --config--> runner
runner: start shards, dispatch, riders on in-memory bus
  each tick: publish clock.ticked, drain
    bus --message--> service shell --input--> brain.decide --outputs--> shell --publish--> bus
    every published message --> onMessage (event log only with keepEventLog)
  --bus nats: same, each service on its own NATS connection, runner records every type,
    waits for 10 ms of quiet instead of drain
runner --each message--> summary (+ invariant checker) --> main.ts prints, exits (no event log kept; --bus nats: runner --{ eventLog, rejected }--> summarize)
--compare: runner twice (greedy, batched), summarize each --> compareSummaries --> main.ts prints table, exits
```

Separate processes (`bun run dev`):

```
dev.ts --Bun.spawn, RUN_ID, REGIONS--> dispatch-0..k-1, riders, driver-shard-0..n-1, clock (one process each, own NATS connection)
each: process shell --connect--> NATS bus --> service wiring --> service shell + brain
clock: wait CLOCK_START_DELAY_MS, then clock.ticked every 1 s / SPEED --> NATS sim.events.clock.ticked
every message: publisher --NATS subjectFor, Run-Id header--> services subscribed to its type (0042) --> its brain
```

Persistence (`bun run dev` spawns the persister; ADR 0029):

```
publisher --NATS sim.events.<entity>.<verb>, Run-Id header--> JetStream stream SIM_EVENTS (kept 24 h)
persister: durable consumer `persister` --fetch <= 10,000 msgs or 1 s (next fetch runs meanwhile, ADR 0044)--> parse --toRow--> insertEvents (async insert, wait)
  insert ok --> ack batch; insert failed --> log, retry (1, 2, 4, 8 s), else leave unacked --> redelivered after 60 s
ClickHouse events (ReplacingMergeTree on run_id, type, tick, stream_seq): redeliveries collapse; exact reads use FINAL
bun run report --> listRuns / runReport --SELECT ... FINAL--> events --> printed
bun run replay --> readRunEvents --SELECT ... FINAL--> events --paced by tick--> NATS replay.<runId>.sim.events.*
readRunEvents --SELECT ... FINAL ORDER BY tick, stream_seq, page by page--> parseMessage --> { tick, streamSeq, message }
```

Events published while the persister is down wait in the stream; core-NATS subscribers (services, UI) never wait on it.

Browser UI (`bun run ui`):

```
serve.ts --GET /--> index.html + bundled main.ts; --GET /config.json--> { natsWsUrl }
main.ts --subscriptionFor(?replay=)--> subject: sim.events.> (live) | replay.<runId>.sim.events.> (replay)
main.ts --wsconnect NATS_WS_URL--> subscribe subject --parseMessage--> applyEvent --> view
view --> startRenderer.show (canvas, each animation frame) + panelRows (side panel)
```

The UI only subscribes; it builds its view from events alone and joins mid-run (ADR 0020). Live and replayed events take the same path after the subscription, so the view and renderer can't tell them apart (ADR 0034).

The start delay is what orders tick 1 after the other services subscribed; nothing waits for them explicitly. Nothing orders dispatch's subscriptions before the shards' start-up `drivers.went_online` either (one message per 5,000 drivers, [0049](adr/0049-publish-drivers-going-online-in-batches.md)): dispatch can miss some or all of them and learns those drivers from their tick-1 `drivers.moved` entries, before it can match the first requests on tick 2 ([0043](adr/0043-learn-drivers-from-moves.md), [Start-up race](performance.md#start-up-race)).

Regions (milestone 21, [0050](adr/0050-split-dispatch-by-region.md)): riders and driver shards set the `region` of every message dispatch takes, published on `<subject>.region-<k>`. Shards route moves by the ownership rule (an idle driver's to its previous cell's region, a busy driver's to its trip's) and idle drivers decline offers from other regions. Each dispatch instance (`dispatch-<k>`) is bounded to its region (its index keeps only that region's drivers, busy ones until freed) and subscribed only to its region's messages plus `clock.ticked`; every other subscriber takes all regions (`<subject>.*`). The runner starts one dispatch per region of `SimConfig.regions` (`--regions` for `bun run sim` and `bun run bench`, default `1x1`); over NATS, `bun run dev` (`REGIONS`) and `bun run loadtest` (`--regions`) start one dispatch process per region (`REGION_INDEX`), every process from the one `REGIONS` value (`serviceProcesses`).

Services never call each other: commands (`request_trip`, `cancel_trip` from riders; `confirm_trip` from drivers waiting at a pickup or dropoff, [0041](adr/0041-confirm-trip-while-waiting.md)), offers, replies (incl. `trip_status` to `confirm_trip`), and events are all bus messages. Dispatch is the only source of `trip.*` events ([0018](adr/0018-dispatch-matching-via-offers.md)). Offers reach every shard (`sim.offers.*`); only the shard owning the driver passes them to its brain (its `accepts`).

## Where decisions live

- Grid geometry, distance, moves, spec grid size (`specGrid`): `src/shared/grid.ts`.
- Region layout, numbering, and which region a cell is in: `src/shared/regions.ts` ([0050](adr/0050-split-dispatch-by-region.md)).
- Message shapes, names, and wire parsing (Zod schemas, `parseMessage`): `src/shared/messages.ts` ([0005](adr/0005-use-zod-for-validation.md), [0016](adr/0016-initial-domain-model.md), `domain` skill). `drivers.moved` carries its moves as parallel arrays (`driverIds`, `xs`, `ys`), each array checked in one pass (`z.custom`, no schema per entry) and branded, the shape known only to `driversMoved` and the readers `forEachMove` / `forEachWentOnline` (a Cell per entry) and `forEachDriverAt` (coordinates only, for dispatch) ([0047](adr/0047-driver-moves-as-parallel-arrays.md)). Parsed cells are checked for shape only; grid bounds are an invariant (`src/sim/invariants.ts`). Driver, trip, rider, and run IDs (branded `RunId`, carried only as the `Run-Id` header) are restricted to `[A-Za-z0-9_-]+` so they are valid NATS subject tokens (`sim.offers.<driverId>`, [0028](adr/0028-nats-bus-subjects-and-delivery.md)). The ten types dispatch takes (all but `clock.ticked`) carry `region`, parsed as 0 when absent so runs stored before regions replay ([0050](adr/0050-split-dispatch-by-region.md)).
- Trip transitions: `src/dispatch/trip.ts`; matching strategies (greedy, batched): `src/dispatch/brain.ts` ([0018](adr/0018-dispatch-matching-via-offers.md), [0030](adr/0030-batched-matching.md)); idle drivers kept across ticks, bounded to dispatch's region, and the nearest idle driver search (grid buckets, rings, linear fallback): `src/dispatch/idle-drivers.ts` ([0036](adr/0036-scale-to-50k.md), [0048](adr/0048-keep-idle-drivers-across-ticks.md), [0050](adr/0050-split-dispatch-by-region.md)); batch assignment solvers (dense: rectangular, transpose, sentinel cost; by nearest query: touched drivers plus nearest untouched, which solver for a batch): `src/dispatch/matching.ts` and `brain.ts` ([0030](adr/0030-batched-matching.md), [0033](adr/0033-scale-fixes.md), [0051](adr/0051-search-untouched-drivers-in-batched-matching.md)).
- Randomness: `src/shared/random.ts`; seed streams per service (child stream named after the service): `src/sim/services.ts` ([0023](adr/0023-own-seeded-prng.md)).
- Driver IDs and shard ownership: `src/sim/services.ts`, from shard index and shard sizes only, so every process agrees.
- Tick pacing: `src/clock/schedule.ts`; service process and UI server config and their defaults: `src/sim/config.ts`.
- Run id: generated by the shell (`src/sim/dev.ts`, `runOverNats`), never by brains; stamped as the `Run-Id` header in `src/bus/nats.ts` ([0029](adr/0029-event-persistence.md)).
