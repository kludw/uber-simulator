# 0060. Drivers earn a share of fares and end a shift at a target

- Status: Accepted
- Date: 2026-10-12

## Context

Milestone 34 ([#338](https://github.com/kludw/uber-simulator/issues/338)) adds driver earnings: drivers keep a share of fares, track what they earn, and decide when to be online or where to drive based on it, building on shifts ([ADR 0032](0032-driver-shifts.md)), fares ([0054](0054-price-trips-with-zone-surge.md)), chasing ([0055](0055-idle-drivers-chase-surge.md)) and preferences ([0035](0035-driver-preferences.md)); analytics report the earnings distribution. Like surge, pooling, ratings and roads ([0056](0056-pool-two-riders-going-the-same-way.md), [0057](0057-weigh-driver-ratings-into-matching.md), [0059](0059-drive-on-a-network-of-rivers-and-bridges.md)) it is a portfolio feature: off by default, outputs byte-identical when off.

Forces:

- A fare is fixed at request by dispatch from the rider's quote (0054), and only `trip.requested` carries it, only with surge on. Drivers never see `trip.requested` (it would be every request to every shard), and their offers carry no price. With surge off no message carries a fare at all.
- Drivers already receive `trip.completed` (or, after a lost one, `trip_status` `completed`, [ADR 0041](0041-confirm-trip-while-waiting.md)) for every trip they finish: one message per trip that exists anyway.
- Hot paths: ratings ([0057](0057-weigh-driver-ratings-into-matching.md)) showed one extra message per completed trip costs about 38 ms of settle at 600k live; `drivers.moved` carries every move. Nothing here may add a message per trip or bytes per move.
- Drivers' online and offline periods come from per-driver seeded schedules (0032); an online period ends only when the driver is idle. Every idle driver chases the nearest surge area in reach (0055).
- Brains are pure and seeded: a new draw takes its own child stream so nothing else shifts.
- Roads (0059, being implemented in [#336](https://github.com/kludw/uber-simulator/issues/336)) make fares road-distance fares, set by dispatch at request.

## Decision

We will give each driver a fixed share of every fare it completes, put the fare on the completion message drivers already get, keep each driver's earnings for its current online period in its driver shard, and, with shifts, end an online period early once the driver has earned its target for it. Off by default.

1. **Driver share**: a driver earns `round(fare × 0.75)` cents for each trip it completes, rounded half up: in integers `(3 × fare + 2) div 4`, which is what `Math.round(fare * 0.75)` gives for every integer fare (0.75 is exact in binary) and what SQL computes as `intDiv(fare * 3 + 2, 4)`; never a float `round`, which in ClickHouse rounds half to even (254 → 190, not 191). Base fares are even, so every odd distance hits the half. `driverShareOf` is the one definition in TypeScript; the summary, the UI, the checker and the driver shard call it (`driverShareOf`; 25% is the platform's, not modeled further). The fare is the trip's, fixed at request (0054): with surge on, the rider's quote; pooled fares 25% off (0056) and the driver earns a share of each of its two riders' fares; with surge off, the base fare (`fareOf` at 1.0, as the summary already counts it); with roads on, by road distance (0059). Cancelled and released trips earn nothing.
2. **The fare reaches the driver on its completion**: with earnings on, dispatch keeps each trip's fare from its request and puts it on `trip.completed` (`fare`) and on `trip_status` with status `completed` at either stage (0041's table replies `completed` to a pickup or dropoff confirm of a trip this driver completed); the driver credits it only at the dropoff stage, while waiting at that trip's dropoff, the one way it leaves `at_dropoff` without `trip.completed`. No new message, no field on offers or moves; `trip.requested` is unchanged (no fare with surge off).
3. **Where earnings live**: each driver shard keeps, by driver index, the driver's earnings in its current online period (cents, an `Int32Array`) and, with shifts, its target (another): 8 bytes per driver, 4.8 MB across the fleet at 600k, only with earnings on. A completion adds the driver share; going offline reports and resets it. Run totals and distributions are views built from events (summary, report, UI); no service keeps them. Dispatch keeps one number per live trip.
4. **Behavior: an earnings target per online period**: each driver draws a target once, uniform in $15-30 (integer cents) from child stream `earnings:<driverId>`; with shifts on, an idle driver whose earnings in this online period reached its target ends the period on that tick, going offline exactly as at a scheduled end (`driver.went_offline`; offline period drawn and counted from then, 0032). A driver on a trip finishes it first, as today. Without shifts there is no period to end, so no target is drawn: earnings on changes no outcome (a driver quitting for the rest of the run would drain short runs). Surge, pooling, ratings and roads change what a trip pays, so they change how soon targets are reached, nothing else.
5. **Going offline reports the period**: with earnings on, `driver.went_offline` carries `earned`, the online period's earnings in cents (per-shift analytics; the checker verifies it).
6. **Invariants** (spec, checker): `fare_mismatch`, a `trip.completed` whose `fare` differs from its trip's fare (`trip.requested`'s, else the base fare by distance: `fareOf` at 1.0, so 25% off for a pooled trip (0056); road distance with roads on); `earnings_mismatch`, a `driver.went_offline` whose `earned` differs from the sum of the driver shares of that driver's `trip.completed` fares since it last went online.
7. **Switch and outputs**: `--earnings on|off` for `bun run sim`, `bun run bench` and `bun run loadtest`, `EARNINGS` for `bun run dev` (dispatch and driver shards; riders unchanged), `SimConfig.earnings`; `bun run sim -- --compare-earnings` runs earnings off and on side by side. With earnings on the summary adds `driver earnings: $<total>`, `per driver: p10 $<a> / median $<b> / p90 $<c>` (over the fleet, $0 for a driver without a trip) and `mean drivers online: <x.x>`, and with shifts `online periods: <n>, median earned $<d>`. Off: no fare kept, no array, no draw, no field; every output and event log byte-identical.
8. **Persistence and report**: no ClickHouse column or migration: the fare and `earned` live in the payload, as fares, `pooled` and stars do. `bun run report` adds the same earnings lines when any `trip.completed` carries a fare: per driver from `sum(intDiv(JSONExtractUInt(payload, 'fare') * 3 + 2, 4))` of `trip.completed` grouped by `driver_id` (rule 1's rounding, so the report equals the summary and `earned` to the cent), quantiles over the fleet (`fleetSize` from `drivers.went_online`) with drivers without a completion at $0; online periods from `driver.went_offline`'s `earned`. Replay republishes them unchanged.
9. **UI**: the panel adds `Driver earnings` (total) once a completion carries a fare, and `Per online period` (mean `earned`) once a `driver.went_offline` carries one. Dots and heatmap unchanged.

Out of scope, deliberately: earnings-aware chasing (see Alternatives), drivers declining offers by fare, going online because of surge, costs (fuel, time), tips, per-driver earnings in the UI, driver share by tier or time, bonuses and guarantees, earnings without shifts changing behavior, stored or replayed targets.

## Rationale

- **The completion is the one message that already goes to the driver once per earned fare**: putting `fare` on it costs a few bytes per completed trip and no message; a field on `offer` would cost bytes on declined and expired offers too and need the driver to hold it until completion; the driver computing the fare itself would need the rider's quote (unknown to it) and, with roads, the network. Dispatch already prices the trip; it only keeps the number.
- **Online-period earnings in the shard, totals as views**: the target is the only decision that needs earnings, and it is per online period; a per-run total in the shard would be state no brain reads. Two typed arrays are the cheapest per-driver state (ADR 0033), and the summary, report and UI already rebuild everything else from events.
- **A target that ends an online period**: the least behavior that uses earnings and stays inside today's model: it only moves the end of a period 0032 already has, so offline drivers, the went-offline event, dispatch and the checker work unchanged. It is a known real effect (income-targeting drivers work less when pay is high), and the spike shows it: under surge, supply drops further. **$15-30** binds in about half the online periods at spec load and two thirds at 10k, for −3% to −7% supply; $10-20 would cut supply by 16-20% and dominate every comparison, $30-60 almost never fires.
- **75%**: a round number near ride-hailing practice; it scales every amount and changes no decision except through the target, which is in the same cents.
- **`earned` on going offline**: one optional field on a message per shift change (not per trip) lets the report show per-shift earnings and the checker verify the driver's arithmetic against the log.

## Alternatives considered

- **Earnings-aware chasing** (chase a surge area only when the expected gain beats the driver's current earnings rate): needs an expected-fare model (constants with no ground truth) and a per-driver rate, and chasing already sends every idle driver toward surge (0055), which 0055's spike found helps; the parent asks for online/offline *or* chasing. Rejected for this milestone; a later ADR can add it on top of the same earnings arrays.
- **Fare on `offer`**: bytes on every offer including declined and expired ones, and the driver holds it per trip. Rejected.
- **Drivers derive fares** from offers and their price view: the quote at request can differ from the shard's last prices; with surge off it would work, with roads it needs the network. Rejected for exactness.
- **A new `driver.earned` event per trip**: one more message per completion, the cost ratings measured. Rejected.
- **Earnings kept by dispatch or a new service**: drivers decide on them, so the driver shard owns them. Rejected.
- **Target per run without shifts** (quit for the rest of the run): drains short README runs (most drivers stop within the hour) and needs a way back online. Rejected; without shifts, earnings are accounting only.
- **Target as an hourly rate** (quit when earnings per online tick exceed a rate): equivalent in expectation for a fixed period length, harder to explain and to check. Rejected.

## Consequences

- **Messages**: optional `fare` on `trip.completed` and `trip_status`, optional `earned` on `driver.went_offline`, present only with earnings on; no new message type or subject.
- **Dispatch**: one switch, the fare kept per trip; with earnings off today's code. Unlike pooling and ratings, earnings need a dispatch switch (`EARNINGS` for dispatch and driver shards).
- **Drivers**: earnings and target arrays by index; the target is one array read per idle driver per tick in the shift loop (shifts only); a completion adds one number.
- **Determinism**: targets come from `earnings:<driverId>` children of the shard stream; nothing else shifts. A completion's fare reaches the driver in the same message that frees it, so earnings are the same on every bus; only loss can move which message brings it.
- **Roads**: fares are dispatch's, so with roads on earnings follow road distance with no change here; the checker's base fare uses road distance once it takes the network (#336f); whichever of that and the earnings invariants lands second keeps both.
- **Performance**: no message added; bench above. The live check measures 600k with earnings on (shifts off, as the load test runs) against off.
- **Docs**: spec (trip lifecycle step 5, invariants, milestone 34), README `--compare-earnings` table, architecture (earnings in driver shards, fare kept by dispatch), domain skill (Earnings section), `docs/ui.md`.
- **Risks**: without shifts nothing behaves differently, so `--compare-earnings` on the default scenarios shows equal outcomes and new lines only; the README pairs it with `--shifts on`. The target's effect at README sizes is close to noise (spec batched 433 → 424, busy greedy 403 → 411); 10k shows it.

Domain terms (domain skill, in this change): **Driver share**, **Earnings**, **Earned** (online period earnings), **Earnings target**.
